AgentVerse

AgentVerse is a multi-agent framework that structures collaborative problem solving into expert recruitment, collaborative decision-making, action execution and evaluation. This repository re-implements that task-solving loop as the workload of our paper (blog post), runs its discussion stage under three coordination topologies, and records every LLM call it makes.

Original work: Chen et al., AgentVerse: Facilitating Multi-Agent Collaboration and Exploring Emergent Behaviors, arXiv:2308.10848. Framework: github.com/OpenBMB/AgentVerse. The workflow here is our re-implementation of its stages, not the original code.

The workflow

An orchestrator (Agent A) runs the stages; worker agents (Agent B) carry out the experts' LLM calls against one shared model backend. A run can loop: a low evaluation score starts another iteration from recruitment.

  1. Expert recruitment

    One orchestrator call reads the task and recruits experts, each with a role and a contract (what it is responsible for). The paper fixes the team at four subagents.

  2. Collaborative decision-making measured

    The experts discuss the approach under one communication structure (below) for up to three rounds, or until they agree. A synthesis call condenses the discussion into a decision. The paper's traffic analysis uses the LLM calls of this stage.

  3. Action execution

    Each expert carries out its part of the decision; the calls run in parallel, one per expert.

  4. Evaluation

    The orchestrator scores the result from 0 to 100 and writes feedback. Below the acceptance threshold (70 by default) another iteration starts, up to the iteration limit (3 by default).

  5. Final synthesis

    A last call writes the answer from the execution results.

Three topologies

Sequential and star are AgentVerse's horizontal and vertical decision-making structures; full mesh is added here as the densest case. The topology is chosen per request with force_structure.

Sequential

horizontal

Agents speak one at a time in a fixed order, each seeing the turns before it. One LLM call is in flight at a time.

Star

vertical

A solver (S) proposes; the other three agents review the proposal in parallel (R) and the solver revises from their critiques. Up to three calls in flight.

Full mesh

full_mesh

Each round, every agent messages every other: N×(N−1) = 12 directed messages for four agents, submitted at once and run five at a time.

How this repository instruments it

  • Services. Agent A, the orchestrator, takes POST /agentverse on port 8101; Agent B workers on ports 8102–8104 forward subtasks to the vLLM backend on port 8000. Each runs in its own container on Docker bridge networks.
  • Every LLM call is recorded in the run's response with a label that names its stage, role and round (for example vertical_reviewer_<role>_iter2 or full_mesh_message_round1_agent2_to_agent3), its UTC start time, duration and token counts, and the backend's own timing. A request ID (X-Request-ID) and the OpenTelemetry trace context travel with each call.
  • Four layers, one time axis. Application: call records and traces (Jaeger). LLM backend: vLLM metrics such as in-flight requests, token throughput and queue wait (Prometheus). Container: CPU, memory and interface counters (cAdvisor). Network: a passive collector on the Docker bridge reconstructs TCP flows and exports bytes and packets per directed service pair and connection events. The layers share agent identifiers and timestamps, so a run's metrics join across them.
  • Controlled variables. Topology, team size and rounds are request parameters (force_structure, force_agent_count, full_mesh_max_rounds); the task source, prompts, model and monitoring stay the same.

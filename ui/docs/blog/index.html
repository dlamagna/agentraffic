Same task, same model, different traffic

How the way LLM agents coordinate shapes the traffic they send to the model server.

Davide Lamagna, Albert Cabellos, Alberto Rodriguez-Natal, Gábor Rétvári, Berta Serracanta

This post is an informal write-up of our NAIC 2026 paper, Towards Traffic Modelling of Multi-Agent Systems: The Role of Coordination Topology. For the method, the statistics and related work, please refer to the paper.

Read the paper (ACM DL) View the code Explore the results

TL;DR

  • The way LLM agents coordinate decides when their calls reach the model server.
  • Agents that fan out send calls in bursts. Agents that take turns send them one at a time. Neither looks Poisson.
  • Two setups can make calls at the same average rate and still load the server differently.

Why look at agent traffic at all?

Most traffic models start with people. Someone clicks, a request goes out, and arrival rates follow human behaviour. Agentic systems break that link. A single task from a user can turn into dozens of model calls, and their timing is set by how the agents coordinate, not by the user.

This is no longer a niche concern. Cloudflare reported in June 2026 that traffic from AI agents and other bots now surpasses that of people. There is a familiar lesson here too: in the 1990s, measurements of Ethernet, wide-area and web traffic showed that Poisson models badly underestimate how bursty real traffic is (Leland et al. 1994; Paxson and Floyd 1995; Crovella and Bestavros 1997). Each new kind of traffic has needed its own model. We wanted to know whether agents are next.

A little background for readers outside networking. A traffic model describes when requests arrive and how much work each one brings, in a form simple enough to reason about. Operators use such models to size servers and links, to set rate limits and autoscaling rules, and to drive simulations and load tests. A model only helps if it matches how the traffic really behaves.

The classic starting point is the Poisson process: requests arrive independently of each other at a constant average rate. The gaps between arrivals then follow an exponential distribution, so a new request is no more likely just after the last one than at any other moment, and a single number, the rate, describes everything. That simplicity made it the default. Queueing results are easy to derive for it, and it described telephone calls well. But it assumes arrivals are spread out fairly evenly. If real traffic comes in bursts, queues typically grow longer and tail latency gets much worse than a Poisson model predicts at the same average load. That gap is what this post is about.

The experiment

Each run hands an AgentVerse workflow a task: a maths problem, a research question, a consulting brief or a small coding job. Four expert agents are recruited, discuss the task, then carry out and evaluate a plan. They all use the same small model, Llama 3.2 3B, served by a single vLLM instance.

The only thing we changed is how the agents discuss:

Sequential

Agents speak one at a time, each seeing the turns before theirs.

Star

One agent proposes a solution and the other three review it at the same time.

Full mesh

Every agent messages every other agent: twelve messages per round.

We ran each pattern about 500 times (481 for star) and logged every model call, alongside metrics from the model server, the containers and the network. Changing the topology also changes how many calls a run makes and how long each one is, so the comparisons below are between whole setups. Most of what follows comes from one simple quantity: the gap between the starts of consecutive model calls during the discussion1.

Bursts, then waiting

When agents take turns, every gap is a few seconds long, roughly the time the model takes to answer. Fan-out changes this. In star, 53% of the gaps are shorter than 50 ms, because the reviews are dispatched together. In full mesh the share is 38%, and for sequential it is 0%. The remaining gaps form a second, slower group set by how long the previous step takes to generate. The arrivals end up bimodal: a burst, then a wait.

In full mesh the twelve peer messages go through a pool of five workers, so only five leave together and the rest follow as workers free up. That is an orchestrator setting rather than a property of the topology, and it caps the size of the burst. We have not measured how much it lowers the 38%.

Poisson doesn't fit

The usual first guess for arrivals is a Poisson process, which implies exponentially distributed gaps. For star and full mesh that fails almost by construction, since calls sent together cannot be Poisson. Sequential is the more interesting case: it has no bursts, and the exponential still fits far worse than the alternatives (KS distance 0.40, against 0.03 for the log-normal).

Looking only at the slower gaps, those above 50 ms, the log-normal has the lowest AIC of the three distributions we tried in every pattern. How close it gets differs. The KS distance is 0.03 for sequential and 0.08 and 0.09 for star and full mesh, so in the fan-out patterns the slow group has structure that a single distribution does not capture. For full mesh the Weibull is slightly closer by KS distance. The fits, tests and robustness checks are in the paper.

Same rate, different load

For us this is the most practical result. Star and sequential make discussion calls at almost the same average rate, about 0.21 per second. Yet star keeps more calls in flight at the model server: 1.6 on average against 1.0. Its calls also take longer, 11.6 s on average against 5.7 s, although part of that is that they are longer (2.7k tokens against 1.8k). Full mesh finishes its discussion in 32 s against 81 s and averages nearly three calls in flight. It sends fewer bytes to the model server in total (39 kB per run against 51 kB), but in so much less time that the mean byte rate is 77% higher, about 1.1 kB/s against 0.6 kB/s.

An average rate hides this. A rate limiter or autoscaler sized on averages would treat star and sequential as the same workload, even though one arrives as a steady trickle and the other in bursts. It also means a bursty trace from an agentic system may just reflect its structure, not a change in load.

Limits

This is one framework, one small model, four kinds of task and a single machine. The topologies were fixed in advance and the agents did not call external tools. The exact numbers are specific to this testbed. We expect the pattern to carry over: fan-out creates bursts, and the coordination structure, not just the user, shapes what the server sees.

Where next

Next we want more models and frameworks, deployments spread over several machines, a mixture model that describes both groups of gaps, and a generative model that can produce synthetic agent traffic. Tool calls and agents that choose their own call graph come after that.

The paper's abstract

Multi-agent LLM systems are an emerging networked workload whose rapid deployment raises questions about the traffic patterns they generate. Compared to conventional applications, these systems generate requests internally: a single user task can induce a structured sequence of model calls whose timing is governed by coordination logic rather than by user arrival rate. It is not clear whether classical traffic models, designed for human-driven workloads, apply to this setting.

We present an empirical characterisation of LLM-call inter-arrival time distributions across sequential, star, and full-mesh agentic coordination topologies, using a multi-layer measurement framework over 500 repeated runs per topology. We find that topology fundamentally shapes the arrival process of requests to the LLM backend: fan-out coordination introduces a structural bimodality absent in sequential execution, and the reasoning-phase component is best described by a log-normal distribution, with the Poisson exponential null model decisively rejected across all topologies. These differences propagate to inference and network level metrics. The framework and analysis pipeline are released openly at https://github.com/dlamagna/agentraffic.
